# 文档站站点地址按项目名推导

延续 流水线接入双平台（见 archive/202610/20261025.md）。

计划位置：本轮第 2 项；前置：无。

## 一、背景

`pages` job 里 `SITE_URL` 直接取 `$CI_PAGES_URL`，而该 CI 预置变量既带完整命名空间路径、又不带尾斜杠（形如 `https://<域名>/<组>/<子组>/<项目名>`）。实际站点只挂在 `/<项目名>/` 下，命名空间路径访问为 404；VitePress 又把 `sitemap.hostname` 当目录做相对拼接，末段路径因此被并入文件名。线上 `sitemap.xml` 实测为 `https://<域名>/develop/工作区/changelog.html`，条目全部指向不存在的地址。

页面样式不受影响（`base` 单独由 `VITEPRESS_BASE` 提供），故该缺陷此前未被发现，只在搜索引擎抓取与分享链接解析时生效。GitHub 侧 `SITE_URL` 显式写死站点地址，不受影响。

## 二、实施方案

改 `.gitlab-ci.yml` 的 `pages` job：

- 新增 `PAGES_ORIGIN`：取 `$CI_PAGES_URL` 的前三段（协议 + 主机），得到站点根。
- `SITE_URL` 默认值改为 `$PAGES_ORIGIN/$CI_PROJECT_NAME/`：站点实际挂在 `/<项目名>/` 下，按项目名拼回并补尾斜杠，供 sitemap / canonical 相对拼接。
- 补三行注释说明 `$CI_PAGES_URL` 的两处偏差（带命名空间路径、不带尾斜杠），避免后续被「化简」回单变量直取。
- `VITEPRESS_BASE` / `REPO_URL` 不动：前者取 `/$CI_PROJECT_NAME/` 与站点实际挂载点一致，后者不参与路径拼接。

`docs/.vitepress/config.mts` 不改：其 `siteUrl` 默认值已带尾斜杠，GitLab 侧由 `SITE_URL` 覆盖。

## 三、影响范围

`.gitlab-ci.yml` 的 `pages` job 新增一行取值、改写一行取值与三行注释。不改源码、不改文档、不改 `.github/workflows/deploy-docs.yml`、不改验收脚本。

## 四、验证方式

- 按 CI 推导结果注入 `SITE_URL=https://<域名>/<项目名>/`、`VITEPRESS_BASE=/<项目名>/` 构建，检查 `docs/.vitepress/dist/sitemap.xml` 的 `<loc>` 落在站点实际挂载点下，与线上可访问地址一致。
- `pnpm verify` 的文档站构建步骤通过（含内链检查）；PHP 侧门禁与本改动无关，本机兼容性缺陷不属本次验收范围。
- 推送后在线上抓 `sitemap.xml` 复核（推送需单独确认）。

## 五、回滚方案

只改一个 CI 配置文件的一行新增与一行取值，`git revert` 对应提交即可恢复，无产物依赖。

## 六、实施结果

- `.gitlab-ci.yml` 的 `pages` job 新增 `PAGES_ORIGIN`（`cut -d/ -f1-3` 取协议与主机），`SITE_URL` 默认值改为 `$PAGES_ORIGIN/$CI_PROJECT_NAME/`，并补三行注释写明 `$CI_PAGES_URL` 的两处偏差；`VITEPRESS_BASE`、`REPO_URL` 与 `docs/.vitepress/config.mts` 未动。
- 按 CI 推导口径注入 `VITEPRESS_BASE=/fxyin/`、`SITE_URL=https://<域名>/fxyin/` 后构建，`docs/.vitepress/dist/sitemap.xml` 的 `<loc>` 落在 `https://<域名>/fxyin/changelog.html`、`/fxyin/config.html`、`/fxyin/contributing.html`；同一地址线上实测 200。
- `pnpm verify` 全绿：`composer check` 五步通过（209 个测试 / 355 断言），`docs:build` 构建通过且零死链。
- 本机 PHP 8.4 直接调用 `openssl_pkey_new()` 返回 `false`，需以 `OPENSSL_CONF` 指向 `php/extras/ssl/openssl.cnf` 才能生成密钥；该前置条件只影响本机跑测试，与本次改动无关，也未写入仓库。

## 20261026-唐启云-修复路径拼接丢失绝对前缀

> 负责人：唐启云　状态：已完成　范围：common　完成时间：2026-10-26 00:31

# 修复路径拼接丢失绝对前缀

## 背景

CI 修复 pnpm 报错后首次真正跑到 `composer check`，PHP 8.2 job 在 PHPUnit 阶段失败：

```text
1) Fxri\Tests\Http\ViewTest::testRender
InvalidArgumentException: 模板不存在：tmp/fxri-view-22633fab/hello.php
```

根因在 `src/File/Path.php` 的 `join()`：它对**每一段**（含首段）执行 `trim($segment, '/')`，`/tmp/fxri-view-xxx` 因此被降级为相对路径 `tmp/fxri-view-xxx`。`View::path()` 用它拼模板绝对路径，`is_file()` 按仓库根解析失败。

### 门禁此前未拦住的三点原因

1. Windows 下 `sys_get_temp_dir()` 形如 `C:\Users\...\Temp`，`normalize()` 识别并保留 `C:/` 盘符前缀，落盘路径仍可用，`ViewTest` 本地必然通过。
2. Linux 下没有盘符，`normalize()` 只在剩余部分以 `/` 开头时才补前导斜杠，而 `join()` 已把首段斜杠 trim 掉，相对路径无人纠正。
3. 此前四个 check job 全部死在 `actions/setup-node` 调用未安装的 pnpm 上，`composer check` 从未在 CI 真正执行，本次是首次暴露。

### 同类问题排查结论

- `src` 内只有 `Http\View` 一处用 `Path::join()` 拼文件系统路径，其余路径均用 `DIRECTORY_SEPARATOR` 手拼或 `tempnam()`，不受该缺陷影响。
- 全仓无 `__DIR__` / `getcwd()` / `chmod` / `PHP_EOL` / locale 类依赖平台差异的断言。
- 结构性缺口：`File\Path` 与 `File\Filesystem` 没有任何单元测试，纯字符串工具缺少跨平台用例，只能靠「在某个系统上碰巧通过」的集成测试兜底。

## 实施方案

1. `src/File/Path.php` 的 `join()` 改为：首段保留前导 `/`、盘符与协议头，其余段两端去分隔符；首段被清空时把前导 `/` 补回，再交给 `normalize()`。与 `normalize()` 的绝对路径语义对齐。
2. 新增 `tests/File/PathTest.php`，用纯字符串断言覆盖绝对路径、盘符、协议头、空段、`.` 与 `..` 消解，跨平台结果一致。
3. 同步 `docs/file.md` 的最小示例注释、`join()` 参数表与注意事项。
4. 新增 changeset 记录 `join()` 行为变化，发版时并入 CHANGELOG。

不采用的备选：在 `View` 里绕开 `join()` 手拼路径。这样只治单个调用点，库内其他使用者仍会踩坑。

## 影响范围

- `Fxri\File\Path::join()` 对绝对入参的输出变化：`join('/tmp', 'a')` 由 `tmp/a` 变为 `/tmp/a`。仓库内唯一调用点 `Http\View` 正是受益方。
- `normalize()`、`filename()`、`extension()`、`Filesystem`、`MediaInfo` 行为不变。

## 验证方式

1. 本地 `node scripts/verify.mjs --skip-code` 确认文档站构建通过（本机无 php / composer，PHP 侧门禁由 CI 执行）。
2. 推送后观察 PHP 8.2 / 8.3 / 8.4 / 8.5 四个 check job 全绿。
3. 回滚：回退本次提交即可，`join()` 恢复旧语义。

## 完成情况

- `src/File/Path.php`：`join()` 首段保留前导斜杠、盘符与协议头，其余段两端去分隔符，首段清空时补回前导 `/`。
- `tests/File/PathTest.php`：新增 `Path` 单元测试，覆盖 `join()` 的绝对路径、盘符、协议头、空段、`.` / `..` 消解与 `normalize()` 的前缀保留。
- `docs/file.md`：同步最小示例注释、`join()` 参数表与注意事项。
- `.changeset/fix-path-join-absolute.md`：记录 `join()` 行为变化。
- 验证：`node scripts/verify.mjs --skip-code` 通过；PHP 侧门禁由 CI 矩阵执行。

> 负责人：唐启云　状态：已完成　范围：common　完成时间：2026-10-26 00:16

# 修复 CI 矩阵 job 找不到 pnpm 的报错

延续 20261025-唐启云-配置双平台流水线（见 archive/202610/20261025.md）

## 背景

GitHub 矩阵流水线的四个 check job（PHP 8.2 / 8.3 / 8.4 / 8.5）全部失败，报错一致：`Unable to locate executable file: pnpm`。

根因在 `.github/workflows/ci.yml` 的 `actions/setup-node@v5`：该版本在未显式给出 `cache` 输入时，会依据 `package.json` 的 `packageManager` 字段与锁文件自动开启缓存。本仓声明 `packageManager: pnpm@10.34.4` 且提交了 `pnpm-lock.yaml`，于是 setup-node 自动选中 pnpm 缓存并调用 `pnpm` 取缓存目录，而该 job 从未安装 pnpm（矩阵内也只跑 `node scripts/verify.mjs --skip-docs`，不需要 pnpm），进程启动即失败，四个版本表现一致。

对照 `.github/workflows/deploy-docs.yml`：它先 `pnpm/action-setup@v6` 再 setup-node，pnpm 在 PATH 上，故文档部署链路正常。

## 实施方案

1. `.github/workflows/ci.yml` 的 setup-node 步骤补 `package-manager-cache: false`，并加中文注释说明「矩阵内不装 node 依赖、不跑 pnpm 步骤，自动缓存会去找未安装的 pnpm」。
2. 不改 `scripts/verify.mjs`、`composer.json`、`package.json`，验收步骤清单真源保持唯一；GitLab 侧使用 `node:20-bookworm` 镜像且不触发该逻辑，无需改动。

不采用的备选：在 check job 前加 `pnpm/action-setup@v6`。矩阵内实际用不到 pnpm，为缓存多装一份工具不划算。

## 完成情况

- `.github/workflows/ci.yml`：setup-node 步骤补 `package-manager-cache: false` 并加中文注释，说明矩阵内不装 node 依赖、不跑 pnpm 步骤，关掉自动缓存以免调用未安装的 pnpm。
- 未改 `scripts/verify.mjs`、`composer.json`、`package.json`，验收步骤清单真源保持唯一；文档部署流水线与 GitLab 配置不受影响。

## 影响范围

仅 `.github/workflows/ci.yml` 的一个步骤输入；不影响 PHP 门禁内容、文档部署流水线与本地 `pnpm verify` 行为。
