# 13 仓升级方案验证

用配了 fxyin 的 13 个业务仓库验证 1.x → 2.x 升级方案：工具能否给准数、矩阵与文档是否覆盖真实用法。本轮只读，不迁移业务代码。

计划位置：本轮第 2 项；前置：升级体检配置适配层。

## 背景

- 13 个仓库分布在不同根目录，10 个仍是 1.x，3 个已升 2.x（样本 11、样本 12、样本 13）。
- 已确认应用目录存在 `application`、`app`、`apps` 三种写法；扩展门面、命名空间、全局函数、排除模块同样来自 1.x 配置，需一并适配。
- `extend/fxri/base` 是各仓库自带副本，版本不统一（例如 样本 1 缺少 1.6.1 才有的 `is_ipv4` 等全局函数），直接套 1.6.1 矩阵会误判。

## 实施方案

1. 配置差异普查：逐仓对比 `base/config.php`、`data/config.php` 与 `data/app/config/*.php`，列出所有变化键并判定"工具要读 / 与迁移无关"。
2. 版本指纹：用 `git ls-tree` 把各仓 `extend/fxri/base` 与 fxyin 仓库 v1.0.0–v1.6.1 标签逐文件比对，得出实际 1.x 版本或"自定义副本"。
3. 逐仓验证：`profile` + `scan` + `baseline --write/--check`；基线写 `.fxri-audit/baselines`，不写业务仓库。
4. 覆盖核对：汇总所有 distinct 门面方法与全局函数，逐个比对矩阵与 `facade_ext` 方法集合，断言框架 API 全部有目标、兜底文案为 0。
5. 2.x 回溯：3 个已升级仓库用 `git worktree` 检出升级前提交（`e8d95818`、`a4e08c4`、`ee2aacb`）到临时目录，跑同样三项后与当前状态对比，再删除 worktree。
6. 结论与路线：输出 13 仓结论表、每仓 S/M/L 路线与首批替换清单。

## 影响范围

只读业务仓库；不在业务仓库写入任何文件。仓库侧仅在 `.git/worktrees` 下产生临时元数据，验证后清除。

## 验证方式

1. 13/13 能出 profile + scan，`baseline --check` 通过。
2. 框架 API 覆盖 100%，兜底文案 0。
3. 13 仓 HEAD 与脏文件数与开始一致，`git worktree list` 无残留。

## 回滚方案

只读流程，无文件改动；异常时删除临时 worktree 与 `.fxri-audit` 产物即可。
