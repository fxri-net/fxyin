# 13 仓升级方案验证

用 13 个配置了 1.x 的样本仓库验证升级方案：工具能否给准数、矩阵与文档是否覆盖真实用法。本轮只读业务仓库，不迁移业务代码。样本以序号代称，映射只存在于会话记录，不入库。

计划位置：本轮第 5 项；前置：升级体检配置适配层。

## 背景

- 13 个样本分布在 4 个根目录，其中 10 个仍是 1.x，3 个已升 2.x。
- 已确认应用目录存在 `application`、`app`、`apps`、`controller` 四种写法；扩展门面、命名空间、全局函数、排除模块同样来自 1.x 配置，需一并适配。
- `extend/fxri/base` 是各仓库自带副本，版本不统一且普遍带本地改动，直接套 1.6.1 矩阵会误判。

## 实施方案

1. 配置差异普查：逐仓对比 `base/config.php`、`data/config.php` 与 `data/app/config/*.php`，列出变化键并判定「工具要读 / 与迁移无关」。
2. 版本指纹：把各仓 `extend/fxri/base` 与 v1.0.0–v1.6.1 逐文件比对，得出实际版本或「带本地改动」。
3. 逐仓验证：`profile` + `scan` + `baseline --write/--check`；基线写 `.fxri-audit/baselines`，不写业务仓库。
4. 覆盖核对：按各仓本地副本的实际声明比对门面方法与全局函数，区分「框架 API」「项目扩展」「本地新增」三类。
5. 2.x 回溯：3 个已升级仓库用 `git worktree` 检出升级前提交到临时目录，跑同样三项后删除 worktree。
6. 结论与路线：输出 13 仓结论表与每仓路线，写入本任务归档，不进文档站。

## 影响范围

只读业务仓库；不在业务仓库写入任何文件。仓库侧仅在 `.git/worktrees` 下产生临时元数据，验证后清除。

## 验证方式

1. 13/13 能出 profile + scan，`baseline --check` 通过。
2. 框架 API 覆盖 100%，兜底文案 0。
3. 13 仓 HEAD 与脏文件数与开始一致，`git worktree list` 无残留。
